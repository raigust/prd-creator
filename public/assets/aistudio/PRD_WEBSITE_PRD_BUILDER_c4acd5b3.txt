# 1. PRODUCT OVERVIEW

## 1.1 Product Summary

PRD Studio adalah web application yang membantu pengguna mengubah ide produk menjadi Product Requirements Document (PRD) yang terstruktur, detail, konsisten, dan siap digunakan sebagai instruksi untuk AI coding agent.

Pengguna tidak perlu menulis seluruh spesifikasi secara manual. Aplikasi menyediakan pilihan terstruktur, checklist, konfigurasi, preset, dan input opsional untuk membantu pengguna mendefinisikan kebutuhan produknya.

Sistem mengubah seluruh pilihan tersebut menjadi dokumen PRD yang mencakup kebutuhan produk, fitur, user flow, UI/UX, business rules, technical specification, security, testing, acceptance criteria, serta instruksi implementasi untuk AI agent.

Prinsip utama produk:

"Describe less. Specify better. Build with clarity."

## 1.2 Problem Statement

Banyak pengguna memiliki ide untuk membuat website atau aplikasi, tetapi kesulitan menerjemahkannya menjadi spesifikasi teknis yang jelas.

Masalah yang ingin diselesaikan:

1. Pengguna tidak tahu struktur PRD yang baik.
2. Pengguna harus menulis terlalu banyak teks secara manual.
3. Prompt sederhana sering menghasilkan implementasi yang tidak sesuai harapan.
4. Pengguna awam tidak memahami istilah seperti authentication, authorization, API, database relationships, dan acceptance criteria.
5. Spesifikasi sering melupakan error states, validasi, keamanan, responsive design, dan aturan bisnis.
6. AI coding agent dapat membuat asumsi sendiri ketika kebutuhan tidak dijelaskan secara spesifik.
7. Dokumen hasil brainstorming sering tidak konsisten atau sulit langsung digunakan untuk implementasi.
8. Pengguna kesulitan membedakan fitur wajib, fitur tambahan, dan fitur yang tidak termasuk dalam scope.

## 1.3 Product Vision

Menjadi alat yang memungkinkan siapa pun menyusun spesifikasi produk digital berkualitas melalui pilihan terstruktur, tanpa harus memiliki kemampuan menulis dokumen teknis atau pengalaman sebagai product manager.

## 1.4 Product Goals

- Mempercepat proses penyusunan PRD.
- Membantu pengguna mendefinisikan kebutuhan produk secara sistematis.
- Menyediakan pilihan yang mendetail untuk berbagai jenis proyek digital.

# 2. PRODUCT PRINCIPLES

## 2.1 Guided, Not Blank

The primary experience must not begin with a giant text editor.

Users should start by selecting the type of project they want to build and answering guided questions.

Free-text input is available only when necessary or useful.

## 2.2 Progressive Disclosure

Do not display every technical option at once.

Show essential questions first. Reveal advanced configuration when:
- The user selects an advanced mode.
- A selected feature requires additional configuration.
- A technical decision materially affects the resulting PRD.

## 2.3 Plain Language First

Technical terms must be explained in simple language.

Example:

Authentication:
"Bagaimana pengguna membuktikan identitasnya saat login?"

Authorization:
"Halaman dan tindakan apa saja yang boleh diakses setiap jenis pengguna?"

Database:
"Data apa saja yang perlu disimpan oleh aplikasi?"

Advanced terminology can be shown as supporting information.

## 2.4 Explicit Decisions

The system must distinguish between:

- Confirmed: explicitly selected by the user.
- Suggested: recommended default.
- Assumed: provisional decision made to complete a specification.
- Unspecified: decision has not been made.
- Not applicable: section does not apply to this project.

Do not present an unconfirmed suggestion as a confirmed requirement.

## 2.5 Agent-Agnostic Output

The default PRD must use standard Markdown, clear headings, stable requirement IDs, explicit acceptance criteria, and framework-independent terminology wherever possible.

The resulting document must not depend on a particular AI provider.

## 2.6 No Artificial Complexity

Do not force users to configure database schemas, API contracts, authentication, or backend architecture when their project does not require those features.

The generated PRD must adapt to the selected project type.

# 4. PROJECT CREATION WIZARD

## 4.1 FR-001: Project Initialization

Priority: P0

The system must allow users to create a new PRD project.

Required fields:
- Project name.
- Project type.
- Short project description.
- Intended output language.

Optional fields:
- Target audience.
- Existing project or new project.
- Project complexity.
- Design reference URL.
- Additional notes.

Project type options:
- Landing page.
- Portfolio.
- Business website.
- Blog or content platform.
- E-commerce.
- Admin dashboard.
- SaaS application.
- Booking or reservation application.
- Internal management system.
- Marketplace.
- API/backend service.
- Other custom application.

Acceptance criteria:
- Users can start with minimal information.
- Required fields display clear validation messages.
- Choosing a project type adjusts relevant future questions.
- The application does not force irrelevant sections on the user.
- The initial project configuration can be edited later.

## 4.2 FR-002: Project Complexity

Priority: P0

Provide three selectable modes.

### Simple
For landing pages, portfolios, and small websites.

Includes:
- Product overview.
- Pages.
- Content.
- Design.
- Responsive behavior.
- Basic interactions.
- SEO and deployment where relevant.

### Standard
For applications with multiple pages, forms, data, and common integrations.

Includes all relevant simple sections plus:
- Roles.
- Feature requirements.
- Business rules.
- Data handling.
- API requirements.
- Error states.
- Testing.

### Advanced
For complex applications, SaaS, and multi-role systems.

Includes relevant standard sections plus:
- Detailed permissions.
- Architecture.
- Database relationships.
- API contracts.
- Integration requirements.
- Security.
- Performance.
- Observability.
- Detailed acceptance criteria.
- Migration and deployment considerations where relevant.

Users must be able to override individual settings regardless of selected mode.

## 4.3 FR-003: Dynamic Question Engine

Priority: P0

The wizard must show questions based on previous answers.

Examples:
- Selecting a static landing page should not require database design.
- Selecting user authentication should reveal login, registration, session, and recovery options.
- Selecting file uploads should reveal file types, size limits, storage, and access rules.
- Selecting payments should reveal payment methods, payment states, transaction verification, and failure handling.
- Selecting multiple user roles should reveal role permissions.
- Selecting a REST API should reveal endpoint, method, request, response, and error configuration.

Acceptance criteria:
- Conditional questions appear only when relevant.
- Changing an earlier answer recalculates dependent questions.
- Answers that become irrelevant are excluded from the generated PRD.
- Previously entered answers should be preserved when practical, so changing a selection does not unnecessarily erase user work.
- The wizard does not generate contradictory requirements because of hidden selections.

# 6. BUSINESS RULES AND USER FLOWS

## 6.1 FR-008: Business Rule Builder

Priority: P0

Users can define rules using a structured editor.

Each rule contains:
- Rule ID.
- Rule name.
- Description.
- Trigger or condition.
- Required system behavior.
- Validation conditions.
- Failure behavior.
- Related feature.

Example:

Rule: Order Quantity Validation

Condition:
The user submits an order.

Validation:
The requested quantity must be a positive integer and cannot exceed available inventory.

Expected behavior:
Reject invalid quantities and display a useful error message.

The builder must also support custom rules using free text.

- Alternative paths.
- Failure scenarios.
- Expected final state.

Preset flows:
- Visitor browsing.
- Registration and login.
- Profile management.
- Create and edit records.
- Search and filtering.
- Checkout and payment, if applicable.
- Booking, if applicable.
- Admin approval.
- Error recovery.

Acceptance criteria:
- Flows are numbered and rendered in the PRD.
- Relevant alternative and failure paths are supported.
- Users can reorder and remove steps.
- Irrelevant preset flows are excluded.
